# §8 例外系

| ケース | 対応 |
|---|---|
| 在庫切れ等でサーバが拒否 | 新 `base`(version+1) を返す。`pending` 削除で自動ロールバック。専用のエラー経路を作らない |
| 別タブでカート変更 | `BroadcastChannel` で `base` を配る。未実装でも次のナビゲーションで自然に直る |
| **チェックアウト画面への遷移** | **`data-client-nav="false"` でフルナビゲーションにする**（既定）。ソフトナビゲーションを避けられない場合のみ、遷移前に cart Fragment の再取得を待つ。古い値で通すと金銭事故になる |
| 戻る/進む・BFCache 復帰 | `pageshow` で cart Fragment を 1 回再取得。Store は生きているがサーバ側が変わっている可能性がある |
| 外部決済からの復帰 | フルリロード扱い。Store は初期化されて snapshot から再構築される（正常動作） |
| ログイン/ログアウト | Store 全体を破棄してフルリロード。部分差し替えで済ませない |
| リダイレクト応答 | クエリパラメータを保持したままフル遷移へフォールバック |

---

## 8.1 例外系の分類

上表は 3 つの群に分かれます。**どの群に属するかで対応が決まる**ので、新しいケースが出たらまずここに当てはめてください。

| 群 | 性質 | 対応の型 |
|---|---|---|
| **A. 自動で直る** | 在庫切れ拒否、別タブ変更 | **何もしない。** 既存の機構（version 比較・pending）が吸収する |
| **B. 明示的に取り直す** | チェックアウト遷移、BFCache 復帰 | **確定値を取り直してから進む。** フルナビゲーション（＝取り直しそのもの）か、Fragment の明示的な再取得。古い値で通すと金銭事故 |
| **C. 全部捨てる** | ログイン/ログアウト、外部決済からの復帰 | **フルリロード。** 部分差し替えで済ませない |

群 A が最も多く、群 C が最も少ない。**群 B に該当するかの判断だけが難しい**ので、§8.3 に基準を置きます。

---

## 8.2 群 A：自動で直るもの

### 8.2.1 在庫切れ等でサーバが拒否

```
1. ユーザが「カートに追加」→ pending に delta → 表示が 3 → 4
2. サーバが在庫切れで拒否。カートは変更されない
3. 応答に snapshot { version: 42, count: 3 } が載る（★ version だけ進む）
4. base をマージ（42 > 41 なので上書き）
5. delta を pending から除去
6. → 表示が 4 → 3 に戻る
```

**専用のエラー経路を作らないこと。** ロールバック関数も、エラー種別の分岐も要りません。詳細は [§5.1.3](05-store.md)。

要求されるサーバ側の実装は 1 点だけです。

> **拒否した場合も version を進めて snapshot を返すこと。**

進めなくても表示は正しく戻ります（マージが無視され、`pending` が消えるだけ）。それでも進めるのは、**「サーバが応答した」ことがログと snapshot に残り、後からデバッグできる**ためです。

エラーメッセージの表示は別の話です。それは通常の UI であり、Store の機構とは無関係に扱ってください。

### 8.2.2 別タブでカート変更

`BroadcastChannel` で `base` を配ります。

```ts
import { mergeSnapshots } from 'zogan/client'

const channel = new BroadcastChannel('zogan:store')
channel.onmessage = (e) => mergeSnapshots(e.data)     // { [name]: snapshot }
```

`mergeSnapshots` は [§5.2.3](05-store.md) と同じ version 比較を通します（[付録 A](appendix-a-api.md)）。**順序が乱れても壊れません。**

**未実装なら、ずれは次のフルロードまで残ります。** [§5.5](05-store.md) により snapshot はキャッシュ不能な応答にしか載らないので、キャッシュされたページへのソフトナビゲーションでは新しい確定値が届きません。自然に直る契機は次の 3 つだけです。

| 契機 | 参照 |
|---|---|
| フルロード（アドレスバー入力、外部からの流入、フォールバック） | [§2.3](02-architecture.md)(a) |
| §8.3 の明示的な再取得（チェックアウト遷移・`pageshow`） | §8.3 |
| キャッシュ不能なページ（カートページ等）への遷移 | [§5.2.2](05-store.md) |

回遊中ずっとソフトナビゲーションが続くと、その間ずれ続けます。**`BroadcastChannel` は「あれば良い」ではなく、複数タブでの回遊が想定される EC では実装を推奨します。** ただし金銭事故には直結しません（§8.3 がチェックアウト直前に取り直すため）。[§9](09-roadmap.md) の必須段階に含めていないのはこのためです。

## 8.3 群 B：明示的に取り直すもの

### 8.3.1 【例外を認めない】チェックアウト画面への遷移

**必ず cart Fragment を再取得する。** ここだけは古い値で通すと金銭事故になる。

「金銭事故」の具体的な中身：

| ずれ | 結果 |
|---|---|
| 表示より実際のカートが少ない | 買ったはずの商品が入っていない。クレーム |
| 表示より実際のカートが多い | 意図しない商品を購入。返金対応 |
| 在庫切れ商品が表示に残っている | 決済後に「在庫がありません」。最悪の体験 |
| 価格が古い | 表示価格と請求額が違う。**景品表示法に触れうる** |

最後の行が重要です。これは UX の問題ではなく法務の問題になりえます。

実装は 2 通りありますが、**既定は 1 つです。**

#### 既定：フルナビゲーションにする

```html
<a href="/checkout" data-client-nav="false">レジへ進む</a>
```

[§7.1](07-client-runtime.md) の例がまさにこれです。フルロードなら Store が破棄され、cart Fragment の取得（`load` trigger）から再構築されるので、**ずれが原理的に起きません**。

**このとき `refreshFragment` を呼ぶ必要はありません。** 傍受していないのでフックを差し込む場所がなく、差し込む理由もありません。フルロードが再取得そのものだからです。

#### 例外：ソフトナビゲーションを避けられない場合

チェックアウトが同じ Partial 構造の中にあり、どうしてもソフトナビゲーションで遷移するなら、**遷移の前に完了を待ちます**。

```ts
// クリック傍受の中。fetch を投げる前
await refreshFragment('/_f/cart-badge')
```

**非同期で「ついでに」行ってはいけません。** 待ち時間が発生しますが、金銭事故のほうが高くつきます。

**この経路を選ぶ前に、本当にソフトナビゲーションが必要か確認してください。** チェックアウトは回遊の終点であり、遷移速度が売上に効く場面ではありません。既定に従うほうが、実装も安全性も単純です。

### 8.3.2 戻る/進む・BFCache 復帰

```ts
window.addEventListener('pageshow', (e) => {
  if (e.persisted) {           // BFCache から復帰
    refreshFragment('/_f/cart-badge')
  }
})
```

BFCache は**ページの状態をまるごと凍結して復元**します。JS のメモリも DOM もそのままです。したがって Store は生きていますが、**凍結中にサーバ側が変わっている可能性があります**（別デバイスでの操作、セッション期限切れ、在庫変動）。

- 再取得は **1 回だけ**。ポーリングしない
- `e.persisted` が false（通常の再訪問）なら何もしない。フルロードなので snapshot から再構築される
- cart 以外の Fragment も再取得すべきかは、その Fragment の TTL で判断する。`s-maxage=30` の在庫表示なら CDN 側で自然に更新される

## 8.4 群 C：全部捨てるもの

### 8.4.1 ログイン / ログアウト

**Store 全体を破棄してフルリロード。部分差し替えで済ませない。**

理由は Store の中身が丸ごと別人のものになるからです。version 比較は「同じユーザの同じカートが進んだ」ことしか表現できません。**ユーザが変わったことを version で表現する方法がありません。**

```html
<a href="/logout" data-client-nav="false">ログアウト</a>
<form action="/login" method="post">   <!-- data-partial / data-fragment を付けない -->
```

属性を 2 つ書くだけで済みます。**ログイン・ログアウトの導線には必ずこれを付けること。**

`pending` に残っていた楽観差分も一緒に消えます。これは正しい挙動です。ログアウト時に未確定のカート操作が残っていても、それは適用されるべきではありません。

### 8.4.2 外部決済からの復帰

決済代行から戻ってくるときは**必ずフルロード**です（外部オリジンからの遷移なので、そもそもソフトナビゲーションになりえません）。

- Store は初期化され、snapshot から再構築される
- `pending` は消える
- **これは異常系ではなく正常動作です。** 特別な処理は要りません

唯一の注意点は、**決済完了後のカート snapshot が空になっていること**です。サーバ側でカートをクリアし、version を進めた snapshot を返してください。

### 8.4.3 リダイレクト応答

**クエリパラメータを保持したままフル遷移へフォールバック。**

ソフトナビゲーションの応答が 3xx だったとき、クライアントはリダイレクト先の HTML を部分差し替えしません（[§7.3.1](07-client-runtime.md) の 3 番）。

```
fetch('/products?color=red', { headers: { 'X-Partial': 'results' } })
  → 302 Location: /login
  → location.assign('/products?color=red')   ★ 元の URL へフル遷移
```

**リダイレクト先ではなく元の URL へ遷移する**点に注意してください。ブラウザが改めてリクエストを送り、同じ 302 を受けて `/login` へ進みます。こうすることで、**リダイレクトのチェーンやクッキー設定をブラウザに正しく処理させられます**。

`fetch` は既定でリダイレクトを追跡（`redirect: 'follow'`）してしまうため、**ソフトナビゲーションの fetch には `redirect: 'manual'` を指定すること**。追跡させると、リダイレクト先の応答が `200` として返り、**ログイン画面の HTML を商品一覧に差し込む事故**が起きます（`X-Partial` ヘッダが無いので実際には §7.3.1 の 6 番で止まりますが、依存すべきではありません）。

**`manual` にしても、ステータスコードでリダイレクトを判定することはできません。**

```ts
const res = await fetch(url, { redirect: 'manual', signal, headers })

res.type      // 'opaqueredirect'   ← これで判定する
res.status    // 0                  ← 302 ではない
res.headers   // 空
```

`redirect: 'manual'` の応答は **opaque redirect** になり、ステータス・ヘッダ・URL のいずれも読めません。判定は `res.type === 'opaqueredirect'` で行うこと（[§7.3.1](07-client-runtime.md) の 3 番）。

**読めなくて困りません。** zogan はリダイレクト先を見ずに元の URL へフル遷移するので、`Location` ヘッダを必要としません。上の例で `/login` を知る必要が無いのはこのためです。

## 8.5 新しい例外ケースの判定

表に無いケースに遭遇したら、次の順で判定してください。

```
1. その状態のずれは、次のナビゲーションまで放置して安全か？
     YES → 群 A。何もしない

2. 金銭・在庫・価格に関わるか？
     YES → 群 B。data-client-nav="false" でフルナビゲーションにする。
            それが選べない場合のみ、遷移前に Fragment の再取得を待つ

3. ユーザの同一性が変わるか？
     YES → 群 C。フルリロード

4. どれでもない → 群 A として扱い、実際に問題が出てから昇格させる
```

4 の姿勢が重要です。**先回りして群 B・C を増やさないこと。** 群 B は待ち時間を、群 C は体験の断絶を代償に払います。実際の問題が観測されてから対処するほうが、正味の体験が良くなります。

ただし **2 だけは例外で、先回りして構いません。** 金銭事故は取り返しがつかないためです。
