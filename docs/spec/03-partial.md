# §3 Partial（差し替え領域）

## 3.1 宣言

```tsx
app.page('/products', (c) => {
  return c.render(
    <Layout>
      <Facets />
      <Partial name="results">
        <ProductGrid items={items} />
      </Partial>
      <Partial name="count">{total} 件</Partial>
    </Layout>
  )
})
```

`<Partial>` は Fresh の同名コンポーネントと同じ意味論です。**囲むだけで、その範囲が差し替え可能になります。** ハンドラを分けたり、別ファイルを作ったりする必要はありません。

props の完全な型は [付録 A](appendix-a-api.md) を参照。

### 3.1.1 命名規則

`name` は次の正規表現を満たすこと。**マーカー（§3.3）に直接埋め込まれるため、エスケープではなく検証で担保します。**

```
^[A-Za-z][A-Za-z0-9_]*(-[A-Za-z0-9_]+)*$
```

- 先頭は英字。以降は英数字・`_`・`-`
- **連続するハイフン `--` と末尾のハイフンを禁止**（HTML コメントの終端 `-->` と紛れる形を作らない）
- 長さは 64 文字以内
- 大文字小文字は区別する

違反したらビルド時（`zogan/vite`）または SSR 時に例外を投げること。黙って通さない。

**1 つのページ内で同じ `name` を 2 回使ってはならない。** クライアントは name からマーカーを一意に引くため、重複すると差し替え先が決まりません。SSR 時に検出して例外にします。

### 3.1.2 ネスト

Partial の入れ子は**許可します**。レイアウトの中に大きな Partial を置き、その中にさらに細かい Partial を置く構成は自然に起こります。

```tsx
<Partial name="results">
  <ProductGrid items={items} />
  <Partial name="pager">…</Partial>
</Partial>
```

規則：

- **親子が同時に要求された場合、サーバは親だけを返す。** 親の HTML には子のマーカーがそのまま含まれるので、親を差し替えれば子も入れ替わり、結果は整合します
- 応答ヘッダ `X-Partial` には**実際に返した領域だけ**を列挙する（この例なら `results` のみ）。クライアントはこれを見て「pager は親に含まれていた」と判断する
- 入れ子の Partial に `mode="append"` を指定することは可能。ただし親が `replace` で差し替えられた瞬間に子の蓄積は失われる。**これは仕様どおりの挙動**であり、無限スクロールの中にさらに無限スクロールを置くような設計を避けること

#### 既定の要求では、子は単独で返りません

上の規則には、既定の設定と噛み合わない帰結があります。

[§7.2.3](07-client-runtime.md) の既定は「現在の DOM に存在する全マーカーの名前」を送るため、**入れ子があれば親子は常に同時要求されます**。したがって「親だけを返す」が毎回発動し、**子が単独で返る経路がありません**。

| やりたいこと | 起きること |
|---|---|
| ページャ操作で `pager` だけを差し替えたい | 既定では `results` も要求されるため、親の `results` ごと返る |
| 結果全体を差し替えたい | 意図どおり |

子だけを差し替えたいなら、そのリンクに `data-partial="pager"` を明示します。ただし [§3.2.4](03-partial.md) のとおり、指定を増やすとキャッシュエントリが分裂します。

**設計としては、まず「子だけを差し替える必要が本当にあるか」を疑ってください。** 親ごと返して困る場面は、親が大きく子が小さいときに限られます。その場合は入れ子をやめ、**兄弟の Partial 2 つに分ける**ほうが単純です。

```tsx
// 入れ子：pager 単独の差し替えに data-partial の明示が要る
<Partial name="results">
  <ProductGrid items={items} />
  <Partial name="pager">…</Partial>
</Partial>

// 兄弟：どちらも既定の要求で単独に返る
<Partial name="results"><ProductGrid items={items} /></Partial>
<Partial name="pager">…</Partial>
```

**入れ子が本当に必要なのは、レイアウト構造上どうしても内側に来る場合だけ**です（大きなレイアウト Partial の中に細かい Partial を置く構成）。その場合は親ごと返ることを受け入れてください。

## 3.2 リクエスト形式

```
GET /products?color=red
X-Partial: results,count
```

サーバは**同じハンドラを再実行**し、指定された領域だけを返す。**props は一切送らない。** 入力は URL と Cookie から再導出する。

**複数領域を同時に返せることは必須。** ページャ操作で件数表示・パンくず・結果一覧を同時更新する必要がある。

> Fresh は「パーシャル専用の別ルートファイル + `skipAppWrapper`」方式を採るが、同じ内容を親ファイルとパーシャルファイルに二重に書く必要が出て利用者が混乱している。**ヘッダ方式を採る理由がこれ。ここは Fresh に揃えない。**

ヘッダで部分取得を要求すること自体は Turbo Frames（`Turbo-Frame:` リクエストヘッダ）に前例があります。zogan が足しているのは**カンマ区切りで複数領域を同時に指定できる**点だけで、これは上の「件数表示とパンくずを同時に更新する」要件から直接来ています。

### 3.2.1 リクエストヘッダ

| ヘッダ | 値 | 必須 |
|---|---|---|
| `X-Partial` | 領域名のカンマ区切り。空白は無視。空文字列は不正 | ○ |

サーバ側では `c.req.partials` として `string[] | null` で参照できます（ヘッダ非在時は `null` = フルページ要求）。[付録 A](appendix-a-api.md) 参照。

### 3.2.2 応答形式

**200 応答の body は、要求された領域のマーカー範囲を宣言順に連結したもの。ラッパー要素を付けない。**

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
X-Partial: results,count
Vary: X-Partial
```

```html
<!--p:results--><article>…</article><article>…</article><!--/p:results--><!--p:count-->842 件<!--/p:count-->
```

規則：

| 項目 | 規則 |
|---|---|
| 順序 | **JSX 上の宣言順**。リクエストの `X-Partial` の並び順ではない。サーバは 1 回のレンダリングで出力するため、宣言順以外を出せない |
| マーカー | **開始・終了マーカーを含めて返す。** クライアントが範囲を再構築するために必要 |
| ラッパー | 付けない。`<html>` / `<body>` も付けない |
| 応答ヘッダ `X-Partial` | **実際に返した領域を宣言順で列挙。** 要求と一致しないことがある（ネスト・領域不在） |
| `Vary` | **`Vary: X-Partial` を必ず付ける。フルページ応答にも付ける。** 詳細は §3.2.4 |
| `Content-Type` | `text/html; charset=utf-8` |
| ステータス | 領域を 1 つ以上返せたなら `200`。それ以外は §3.2.3 |

`<script type="application/json" data-store>` は、**それが Partial の内側にある場合のみ**応答に含まれます（マーカー範囲をそのまま切り出すため）。この帰結は重要です。

> **Store の snapshot を差し替えのたびに更新したいなら、その `<script data-store>` を Partial の内側に置くこと。** 外に置いた snapshot はフルロード時にしか届きません。

**ただしこれは、そのページがキャッシュ不能な場合に限ります。** `public, s-maxage=N` を返すページでは、Partial の内側・外側を問わず snapshot を出力できません（[§5.5](05-store.md) の不変条件）。キャッシュされる殻に共有確定値を載せる経路は存在しない、と理解してください。カートのように毎回最新化したい値は Fragment の応答で運びます（[§5.2.2](05-store.md)）。

### 3.2.3 応答の異常系

サーバ側の規則。クライアント側の対応は [§7.3](07-client-runtime.md)。

| 状況 | サーバの応答 |
|---|---|
| 要求された領域を 1 つも出力しなかった | `200` + 空 body + `X-Partial:`（空）。クライアントはフォールバックする |
| 要求のうち一部だけ出力した | `200` + 出力できた分。`X-Partial` に実際の内容を列挙 |
| ハンドラがリダイレクトを返した | **`3xx` をそのまま返す。** 部分応答に変換しない |
| ハンドラが 4xx / 5xx を返した | **そのステータスのまま返す。** `X-Partial` は付けない |

**部分応答の中にエラー画面を埋め込まないこと。** 差し替えが成功したように見えて、ページの一部だけがエラー表示になる状態を作ります。壊れた画面を出さないという原則（[§7.3](07-client-runtime.md)）に反します。

### 3.2.4 Vary によるキャッシュ分割

**`Vary: X-Partial` は、部分応答とフルページ応答の両方に付けます。** ミドルウェアが `app.page` の全応答に機械的に付けること。ハンドラの責務にしない。

#### 片方だけに付けると壊れる

「部分応答にだけ付ければよい」と考えると、次が起きます。

```
1. 初回訪問（ヘッダ無し）→ フルページ応答。Vary が無いのでキャッシュキーは URL だけ
2. CDN がこれを保持する
3. ソフトナビゲーション（X-Partial: results,count）
   → キャッシュキーは URL だけなので 2 がヒットする
   → フルページの HTML が返る。応答に X-Partial ヘッダが無い
4. → §7.3.1 の 6 番に該当 → フォールバック
```

**壊れた画面は出ませんが、ソフトナビゲーションが恒久的に死にます。** 毎回フルナビゲーションに落ちるだけなので、動作としては正しく、遅いだけです。**CDN が冷えているローカル開発では絶対に再現しません。** 本番で CDN が温まってから、原因不明の「遷移が速くならない」として現れます。

逆に部分応答から `Vary` が抜けた場合は、CDN が部分応答をページ本体としてキャッシュし、**全ユーザに `<html>` の無い壊れた HTML を配ります**。こちらは即座に気付けます。

#### 代償：キャッシュエントリの分裂

`Vary` を正しく付けた上で、**代償があることを理解して使ってください。**

| 経路 | 送るヘッダ | 使うキャッシュエントリ |
|---|---|---|
| 初回訪問・フルリロード | 無し | **フルページ版** |
| ソフトナビゲーション | `X-Partial: results,count` | **部分版**（別エントリ） |

**ソフトナビゲーションはフルページ版のキャッシュヒットを利用しません。** 同じ URL でも別物として扱われます。

エントリ数は「2 倍」では済みません。[§7.2.3](07-client-runtime.md) の既定は**遷移元**の DOM にあるマーカー集合を**遷移先**の URL へ送るため、同じ URL に対して次の数だけエントリができます。

```
1（フルページ版）＋（その URL へ遷移してくる元ページの、マーカー構成の種類数）
```

一覧・カテゴリ・検索結果がどれも `results,count` を持つなら、遷移元が何種類あってもエントリは 2 つです。**構成が揃っているほど有利**で、これが既定を「DOM の全マーカー」にしている理由です。

帰結：

- ヒット率は**それぞれのエントリごとに**積み上がる。分裂させるほど各エントリのヒット率が落ちる
- **同じ `X-Partial` の値を使い回すほどヒット率が上がる。** ページ間で Partial の名前と構成を揃えることが、そのままキャッシュ効率になる
- リンクごとに `data-partial` をばらばらに指定すると、**その組み合わせの数だけキャッシュが分裂する**。指定は必要な場合に限ること

[§4.1.3](04-fragment.md)「穴を開けすぎない」と同じ種類の運用注意です。**`Vary` を付けたのに CDN ヒット率が上がらない場合、まず `X-Partial` の値のばらつきを疑ってください。**

## 3.3 領域マーカー

ラッパー `<div>` を挟まない。コメントノードで範囲を区切る。

```html
<!--p:results-->
<article>...</article>
<article>...</article>
<!--/p:results-->
```

理由：商品グリッド（CSS Grid）、価格表（`<tbody>`）、`<select>` の中身は、ラッパー要素を 1 つ挟むだけでレイアウトが壊れる。

クライアントは開始・終了コメントの間の兄弟ノードを置換する。

### 3.3.1 マーカーの形式

```
開始: <!--p:NAME-->
終了: <!--/p:NAME-->
```

- `NAME` は §3.1 の正規表現を満たす。**検証済みなのでエスケープは行わない**
- マーカーの前後に空白を入れない（`<!-- p:results -->` は不正）
- 開始と終了は**必ず同じ親ノードの直接の子**であること

最後の制約が実装上いちばん効きます。開始マーカーと終了マーカーが違う親に属していると「間の兄弟ノード」が定義できません。JSX で `<Partial>` が単一の位置に展開される限り自然に満たされますが、**HTML を文字列で組み立てる経路を作らない**ことでこれを保証します。

### 3.3.2 差し替えアルゴリズム

```
replaceRange(name, newNodes, mode):
  start = 走査して <!--p:name--> を探す
  end   = start 以降で <!--/p:name--> を探す
  見つからない → フォールバック（§7.3）

  parent = start.parentNode
  end.parentNode !== parent → 例外（§3.3.1 違反）

  mode = replace:
    start.nextSibling 〜 end.previousSibling を削除
    newNodes を end の直前に挿入
  mode = append:
    newNodes を end の直前に挿入
  mode = prepend:
    newNodes を start の直後に挿入
```

**マーカー自身は削除しない。** 差し替え後も同じ位置に残り、次回の差し替えに使われます。

サーバが返す HTML にはマーカーが含まれている（§3.2.2）ため、クライアントは受け取ったマーカーを**取り除いてから**中身を挿入します。二重にマーカーが積み重なることを防ぐためです。

### 3.3.3 配置してよい場所

マーカーは HTML コメントなので、**コメントが許される位置ならどこでも置けます**。これがラッパー方式に対する具体的な優位点です。

| 場所 | ラッパー `<div>` | コメントマーカー |
|---|---|---|
| CSS Grid の直接の子 | ✗ グリッド行が崩れる | ✓ |
| `<table>` / `<tbody>` の中 | ✗ HTML パーサに追い出される | ✓ |
| `<select>` の中（`<option>` 群） | ✗ 不正な HTML | ✓ |
| `<ul>` の中（`<li>` 群） | ✗ リストマーカーが乱れる | ✓ |
| Flex コンテナの直接の子 | ✗ 折り返し・`gap` が変わる | ✓ |

上の 5 つはすべて EC の実画面で踏みます。商品グリッド、価格表、バリアント選択、ファセット一覧、タグ列。

## 3.4 mode

```tsx
<Partial name="results" mode="append" key={page}>
```

| mode | 動作 | 用途 |
|---|---|---|
| `replace` | 既存の中身を差し替え（既定） | 通常の遷移、ファセット絞り込み |
| `append` | 既存の後ろに追加 | 無限スクロール、レビューの追加読み込み |
| `prepend` | 既存の前に追加 | 新着通知 |

**`append` / `prepend` では `key` を必須とし、無ければビルド時または実行時に警告を出す。** key がないと Preact が新旧の子要素を区別できず、描画バグになる。無限スクロールでは確実に踏む。

mode と key はどちらも Fresh の `<Partial>` にそのまま存在します。**名前も意味論も変えないこと。**

### 3.4.1 key の要件

| 要件 | 内容 |
|---|---|
| 型 | `string` または `number` |
| 一意性 | **同じ Partial に追加される各バッチの間で一意**であること。ページ番号・カーソル・オフセットが自然な選択 |
| 安定性 | 同じ内容を再取得したとき同じ値になること。`Date.now()` や乱数を使わない |
| 検証 | `mode` が `append` / `prepend` で `key` が無ければ**ビルド時に警告、実行時に開発ビルドでは例外**。本番ビルドでは `console.warn` に留め、描画は続行する |

本番で例外にしない理由は、**壊れた描画のほうがまだ真っ白な画面よりマシ**だからです。ただし開発時は必ず気付ける必要があるので、そこは止めます。

### 3.4.2 mode の選び方

判断は「**その領域は URL の状態を表現しているか、それとも蓄積か**」で決まります。

| 画面 | mode | 理由 |
|---|---|---|
| ファセット絞り込み | `replace` | URL が結果を一意に決める。戻る/進むで再現できる必要がある |
| ページャ（1 → 2 ページ目） | `replace` | 同上 |
| 「もっと見る」ボタン | `append` | URL は変わらない。蓄積が意図 |
| 無限スクロール | `append` | 同上 |
| リアルタイム通知 | `prepend` | 新しいものが上 |

`append` を選んだ領域は、**戻る/進むで正確に再現できません**（蓄積された状態は URL に載っていないため）。これは仕様上の制約として受け入れます。無限スクロールで正確な復元が要るなら、URL にオフセットを載せて `replace` にするのが正しい設計です。
